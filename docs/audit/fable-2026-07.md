## Architecture (as mapped during the audit)

mcpbridge is two cooperating processes plus shared docs, NOT the "Go library" the brief describes (that library was removed per README/History; the current shape is a C wrapper + Go daemon). (1) The C wrapper `mcpbridge connect <config.json>` (wrapper/src/*.c) is launched by the MCP client in place of the real server. It fork/execs a stdio child (or dials a localhost HTTP MCP endpoint), bridges every JSON-RPC line agent<->backend verbatim, and best-effort connects to the daemon over a Unix domain socket to receive reload notifications. (2) The Go daemon `mcpbridge-daemon` (daemon/) runs once per user session, scans ~/.config/mcpbridge/*.json configs, listens on the UDS, and fsnotify-watches each registered wrapper's child binary; when a binary changes on disk it pushes a targeted `reload` to the matching wrapper(s). The wire protocol (docs/wire-protocol.md) is newline-delimited JSON envelopes with a `t`/`v`/`seq` header and per-connection monotonic seq for request/response correlation (hello/hello_ok, register/register_ok, reload/reload_ack, deregister, shutdown, error).

Daemon concurrency model: `socket.Server` accepts connections in `Run` and spawns one goroutine per connection (`conn.serve`). Shared state is `s.conns` (map keyed by internal id) plus `s.regH`, both guarded by `s.mu`. Push methods (BroadcastReload, ReloadName, ChildBinaryForName, BroadcastShutdown, Registrations) are called from other goroutines (SIGHUP handler, fsnotify timer callbacks) and iterate `s.conns` under `s.mu`. Per-connection writes are serialized by `conn.writeMu`; `conn.seq` is an atomic. The fsnotify watcher (watcher/watcher.go) has its own `w.mu` guarding byName/byFile/dirs/pending maps, with debounced (300ms) reload firing via time.AfterFunc goroutines that then call back into the server's ReloadName. Lock order is consistent (w.mu then s.mu; the server never calls OnRegister/OnDeregister while holding s.mu), so no inversion — but see invariants for a name-keyed tracking bug.

Wrapper concurrency model: single-threaded event loop (main.c run_loop) built on poll() over three fds (agent stdin, child stdout / HTTP fd, daemon socket). No threads; a signal handler only sets a sig_atomic_t flag. Framing is handled by the streaming `mcp_reader` (mcp.c) on each input; parsed messages route through `dispatch` (dispatch.c), which maintains an FSM (fsm.c: STARTING/RUNNING/DRAINING/SWAPPING/RESPAWN/FAILED), an in-flight request counter, a queue of messages held while not RUNNING, and cached initialize/initialized bytes replayed to a freshly spawned child so the agent's session survives a backend swap invisibly. The daemon socket goes non-blocking after the synchronous 5s handshake.

## Load-bearing invariants

- Exactly one daemon binds the socket path per user session. VIOLATED: socket.NewServer (server.go:96) unconditionally os.Remove()s any existing socket BEFORE net.Listen, and there is no flock/lockfile/peer-cred guard. The code comment claims 'the bind below will fail' if a live daemon owns the socket — but the file was already unlinked, so a second daemon silently succeeds, orphaning the first (its socket inode unlinked, its connected wrappers stranded) and stealing all new wrappers.
- The line-framing cap must be identical on both peers. VIOLATED: docs and MaxLineBytes say 256 KiB and the C wrapper's reader uses 256 KiB (daemon_client.c:159), but the daemon's bufio.Reader is only 32 KiB (server.go:296), so ReadSlice returns ErrBufferFull at 32 KiB. MaxLineBytes (256*1024) is used only in the error string, never for enforcement; any spec-legal 32-256 KiB envelope is rejected and the connection dropped.
- conn.reg must be safely published before other goroutines read it. VIOLATED: conn.serve assigns c.reg without holding s.mu (server.go:350-356) while Registrations/BroadcastReload/ReloadName/ChildBinaryForName read c.reg under s.mu — a data race on the pointer (and BroadcastReload/ReloadName also dereference c.reg.Name after releasing the lock).
- Watcher tracking must survive per-connection lifecycle when multiple wrappers share a name. VIOLATED: watcher keys byName/byFile by config name, not connection. Two wrappers registered with the same name (server.go documents this as 'unusual but legal') => the second OnRegister replaces the first's watched path, and the FIRST wrapper's OnDeregister calls Untrack(name) which wipes the watch entirely, so the still-connected second wrapper's binary is no longer watched.
- in_flight must equal the number of outstanding child requests so IN_FLIGHT_ZERO fires only when drain is truly complete. HAZARD: messages queued while not RUNNING are enqueued without in_flight++ and drain_queue (dispatch.c:475-490) forwards them to the child still without in_flight++, yet their responses decrement in_flight (guarded >0). Their responses can therefore decrement counts belonging to genuinely in-flight requests, driving in_flight to 0 prematurely and triggering an early swap/IN_FLIGHT_ZERO while requests are still outstanding. The code comments acknowledge the counting is best-effort.
- A reload notification, once needed, is eventually delivered and acked. HAZARD: the wrapper holds a single pending_reload_seq; a reload arriving while one is in progress is logged and dropped (main.c:384-389) with no re-detection until the next fsnotify event or daemon restart, so a genuinely-needed reload can be lost.
- The RESPAWN FSM state must be able to recover. DEAD PATH: FSM_EV_BACKOFF_EXPIRED (the only edge out of RESPAWN) is never emitted anywhere in main.c, and on child crash while RUNNING the loop breaks because state != SWAPPING (main.c:678). The entire respawn_limit / RESPAWN machinery is unreachable-to-recovery; an unexpected child crash simply exits the wrapper.

## Trust boundaries

- Daemon UDS ingress: any local process running as the same user can connect (socket is 0600 in a 0700 dir, but there is NO SO_PEERCRED/getpeereid check). Untrusted bytes enter at conn.readEnvelope/Unmarshal (server.go:421-434, protocol.go:87) — malformed JSON, wrong version, missing type, oversized lines.
- Wrapper<-daemon socket: daemon replies parsed in daemon_client_try_read/parse_line (daemon_client.c:286-370) and during the blocking handshake (read_line_blocking, 5s timeout).
- Wrapper<-child stdout: arbitrary bytes from the wrapped MCP server framed by mcp_reader and parsed by mcp_msg_parse (child_on_message, main.c:547; mcp.c:77).
- Wrapper<-agent stdin: JSON-RPC from the MCP client, framed by mcp_reader and routed via dispatch_on_upstream (main.c:651-659, dispatch.c:267).
- Wrapper<-HTTP upstream: untrusted network bytes from the localhost HTTP MCP server — status/header parsing, Content-Length (strtol), chunked decoder (hex strtol), and SSE parsing in transport_http.c (~lines 330-490, 578, 730-810).
- Config files on disk: config_load/ParseBytes parse JSON, expand ~/~user via passwd lookups, and validate URLs (config.c:185, config.c:57 expand_tilde, config.c:108 validate_url; Go side config.go:95).
- Environment-controlled paths: $MCPBRIDGE_SOCKET, $HOME, $TMPDIR, $XDG_RUNTIME_DIR, $MCPBRIDGE_CONFIG_DIR feed socket/config path construction (path.go, main.c:127 resolve_daemon_socket_path). sockaddr_un length is checked (daemon_client.c:139); PATH_MAX snprintf truncation is silent.

## Strategic recommendations

## Strategic observations

**1. The daemon's concurrency contract is asserted but not enforced anywhere.** The `Server` doc comment promises "safe for concurrent use: all public methods take the internal mutex," yet the verified `conn.reg` data race (server.go:350) shows the *internal* serve path violates the very invariant the public API depends on. This is a class-of-bug signal, not a one-off: shared `*conn` fields are published on the serve goroutine while push methods (BroadcastReload/ReloadName/ChildBinaryForName/Registrations) read them on the SIGHUP and fsnotify-timer goroutines. The root cause is that `s.mu` is treated as guarding *the map* rather than *the objects reachable through the map*. Any future field added to `conn` and read by a push method will inherit the same latent race. **Systemic fix:** establish a rule that every `*conn` field observable via `s.conns` is written only under `s.mu`, and encode it — ideally by making `conn.reg` an atomic pointer or by funnelling all publication through a single locked helper. Then close the detection gap: **CI runs `go test ./...` with no `-race` (Makefile:36-37)**, so this entire dimension is invisible to the pipeline. Adding `-race` to the daemon test job is the highest-leverage single change in this audit, because it converts a whole category of latent bugs from "ships silently" to "fails CI."

**2. The two peers do not share a single source of truth for the wire protocol.** The 32 KiB vs 256 KiB frame-cap mismatch (server.go:296 vs daemon_client.c:159 and docs/wire-protocol.md) is one instance of a deeper problem: the C wrapper, the Go daemon, and the prose spec each independently restate protocol constants (line cap, header shape, `t`/`v`/`seq` semantics, envelope types) with no shared definition and no conformance test crossing the language boundary. `MaxLineBytes` exists but is dead as an enforcement mechanism — used only in an error string that now actively lies about the limit it enforces. **Recommendation:** treat docs/wire-protocol.md as normative and add a cross-peer conformance test (feed spec-boundary frames — a 256 KiB-minus-one envelope, a 256 KiB-plus-one envelope — through both readers and assert identical accept/reject). Until the two framing readers derive their cap from one agreed constant, they will drift again.

**3. Failure-recovery paths are the weakest part of the design, and they cluster.** The architecture notes independently flag three recovery defects that a fixing engineer should treat as one theme: the RESPAWN FSM state is unreachable-to-recovery (`FSM_EV_BACKOFF_EXPIRED` never emitted; child crash while RUNNING just exits the wrapper, main.c:678); a needed reload can be permanently lost because the wrapper holds a single `pending_reload_seq` and drops any reload arriving mid-reload (main.c:384-389); and the `in_flight` counter can hit zero prematurely because queued-while-not-RUNNING messages are forwarded without incrementing but their responses decrement (dispatch.c:475-490). Individually these are "best-effort" per the code comments; collectively they mean the wrapper's headline feature — invisible backend swap with session survival — has no dependable recovery when anything goes wrong during the swap. This is where a reviewer should focus design attention, because these are correctness-of-the-core-value-prop issues, not edge hardening.

**4. Two singleton/identity invariants are structurally unguarded.** The daemon's "exactly one daemon per session" invariant is defeated by its own startup: `socket.NewServer` unconditionally `os.Remove()`s the socket before `net.Listen` (server.go:96), so a second daemon silently steals the socket and strands the first's wrappers — the guarding comment describes a bind-failure that can never happen because the file is already unlinked. Separately, the watcher keys `byName`/`byFile` by *config name* rather than *connection*, so two same-named wrappers (documented as "unusual but legal") corrupt each other's watch state on register/deregister. Both are the same shape of bug: **a uniqueness assumption baked into a data-structure key that the surrounding code does not actually enforce.** Fixes should either enforce the uniqueness at ingress (peer-cred'd lockfile/flock for the daemon; reject duplicate names) or make the keys connection-scoped so the assumption isn't load-bearing.

**5. Trust-boundary posture is "same-user = trusted," which is defensible but undocumented and unenforced at the daemon.** The UDS has no `SO_PEERCRED`/`getpeereid` check; any same-user process can speak the protocol. That is an acceptable model for a per-user daemon, but it means every ingress parser (readEnvelope/Unmarshal, the HTTP transport's `strtol`/chunked/SSE decoders, config tilde/URL expansion) is the actual security surface and must be robust to hostile-but-same-user bytes. The frame-cap bug already demonstrates one ingress parser diverging from spec. A reviewer handing this off should state the trust model explicitly (in wire-protocol.md) so future contributors don't add a genuinely privileged code path on top of an unauthenticated socket.

**Handoff priority:** (a) add `-race` to CI and fix the `conn.reg` publication; (b) unify the frame cap and add a cross-peer conformance test; (c) treat the three recovery defects (RESPAWN dead path, dropped reload, in_flight miscount) as one workstream; (d) close the daemon-singleton and watcher-name-keying holes together.
